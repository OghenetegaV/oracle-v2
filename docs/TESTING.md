# Testing Oracle

Oracle's tests use the standard library's `unittest` only. They are split into four **tiers** so the everyday command is fast and
the expensive ones stay one command away. **No test is skipped or removed to achieve this**: an unselected test is simply not
loaded, and `python -m tests all` runs every one.

## The commands

| I want | Command | Tiers | Tests | Typical time |
|---|---|---|---|---|
| **The everyday suite** (default) | `python -m unittest discover -s tests -t .` | unit + integration | 610 | ~15-45 s |
| The fastest inner loop | `python -m tests unit` | unit | 250 | ~1.2 s |
| Integration only | `python -m tests integration` | integration | 360 | ~17-45 s |
| **The real architectural drawing** | `python -m tests slow` | slow | 22 | ~80 s (up to ~3 min on a loaded machine) |
| Everything except release-only | `python -m tests full` | unit + integration + slow | 632 | ~1.5-2 min |
| **Complete regression** (before a release) | `python -m tests all` | every tier | 633 | ~1.5-3 min |
| See what is in each tier | `python -m tests --list` | | | |
| The slowest tests of a run | `python -m tests dev --durations 15` | | | |

`python -m tests <selector>` is the same as setting the environment variable and running the plain command. Use whichever suits your shell:

```
python -m tests all                                   # any shell
ORACLE_TESTS=all python -m unittest discover -s tests -t .           # Git Bash / Linux / macOS
$env:ORACLE_TESTS = "all"; python -m unittest discover -s tests -t .  # PowerShell
```

`ORACLE_TESTS` takes a tier (`unit`, `integration`, `slow`, `release`), an alias (`fast` = unit, `dev` = unit + integration, `full` = unit + integration + slow,
`all` = every tier) or a comma-separated list (`unit,slow`). Unset means `dev`. An unknown name is an error, never silently ignored. When tests are left out the
run prints one line saying how many and how to run everything.

Naming a module, class or test always runs exactly that, whatever its tier: `python -m unittest tests.test_real_architectural_drawing` runs the real-drawing
tests, and `python -m unittest tests.test_levels_hardening.EngineerChangesToLevels.test_...` runs one test. So does a custom pattern
(`discover -s tests -t . -p "test_real*.py"`). Tier selection applies only to discovery with the default file pattern.

(This replaced the earlier `ORACLE_SKIP_REAL_DWG` switch; there is now exactly one mechanism.)

## The tiers

| Tier | What belongs in it | Rule of thumb |
|---|---|---|
| **unit** | Pure domain/core logic and small pure functions: the building model, decisions, issues, provenance, value status, interpretation sets and effects, schema migration on JSON fixtures, naming and layer rules, reconciliation rows, static scans of the code base, the tier mechanism itself | no synthetic drawing, no subprocess, no real drawing |
| **integration** | Several Oracle subsystems together: synthetic DXFs built in memory (`tests/drawing_factory.py`), the ingestion + interpretation pipeline, engineer review and resolution on interpreted projects, the legacy-GA adapter on its fixtures, fresh-process import checks | suitable for normal development |
| **slow** | The real squash-court architectural drawing (converted by the ODA File Converter to a 65 MB DXF, read, interpreted; then traced, resolved and projected) | materially longer than everything else together |
| **release** | Needs external software and is not worth running on every change: the ODA File Converter on a small DWG | run by `all` before a release |

The classification of every test class is in the table below and is enforced: **`tests/test_tiers.py` fails if any test class lacks an explicit
`@tier(...)`**, if a test that touches the real drawing is not `slow`/`release`, or if the default selection would include a slow or release test.
Adding a test means adding `from tests.tiers import tier` and `@tier("unit" | "integration" | "slow" | "release")` above its class (or above one method,
to give a single test a different tier from its class). If you are unsure, use `integration`.

## Timings and what dominates them

Measured on the development machine (Windows, Python 3.14, ODA File Converter 27.1, 11.7 GB RAM with AutoCAD and an editor open):

| Selection | Tests | Wall time |
|---|---|---|
| **Before tiers**: the only command ran everything (555 tests) | 555 | 40 s when the machine was idle; 48 s measured with per-test timing |
| Same everything today (`all`, 569 tests: the 555 plus 14 tests of the tier mechanism) | 569 | 61 s |
| **Default (dev)**: unit + integration | 610 | 15 s before the interface phase; 17-45 s now (the Tk tests add about 7 s; the rest is machine load) |
| unit | 250 | **1.2 s** |
| integration only | 360 | 16-45 s |
| slow: the real drawing (+ the interface workflow on it) | 22 | 78 s |
| release | 1 | 0.5 s |

The real drawing's time depends heavily on free memory: with the machine under memory pressure (AutoCAD plus a concurrent run) the same tests took 2-3 minutes. The
default suite has no such dependence.

* The real drawing is roughly **three quarters** of the old suite: a 14 s DWG-to-DXF conversion, a 28 s pure-Python read of 24,159 entities, then about 1 s per
  test that clones the resulting 7 MB project. Those times are production behaviour and are deliberately not reduced (no mocks, no cached substitute for the read).
* The largest default-suite costs are the legacy-GA adapter tests (about 4 s: the legacy parser really runs on a 1.1 MB structural GA) and the interpretation
  pipeline running on synthetic drawings (about 25 ms each, some 200 times). Neither has a hot spot to remove without weakening what the tests do.
* Timings vary with machine load: an open AutoCAD session or a virus scanner touching the 65 MB temporary file can double the slow tier.
* `python -m tests <selector> --durations 15` lists the slowest tests of any run.

## Environment notes

* `ODAFileConverter.exe` is needed for the slow and release tiers; without it (or without the sample drawing) those tests are skipped with a message rather than failing.
* On a Windows console that is not UTF-8, importing the legacy `config.py` prints a check mark and can fail with an encoding error; run with `PYTHONIOENCODING=utf-8` (PowerShell: `$env:PYTHONIOENCODING = "utf-8"`).
* The tests write only to temporary directories. They never modify `input_dwgs/`.
